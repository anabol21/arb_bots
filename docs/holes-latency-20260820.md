## 1. Откуда «дыры по 5 минут»

Уплотнитель пишет один `parquet` на все имена за календарные 5 минут UTC. Журнал покрытия помечает пару (имя, слот 5 мин) неполной, если в слот попал `ws_disconnect`. Отсюда язык «неполных 5-минутных окон»: **4217** за длинный процесс PID 624911.

Это **не** значит, что сокет лежал пять минут.

Факт по журналу `runtime.log.1` за **19 августа 00:00–17:17 UTC** (ротация срезала 16–18-е):

| Показатель | Значение |
|------------|----------|
| Обрывов / восстановлений | 1158 / 1158 |
| Восстановление в том же слоте 5 мин | 1146 (99 %) |
| Восстановление через границу слота | 12 |
| Длительность, с: p50 / p99 / max | 2 / 4 / 1134 |
| Дольше 5 с / 60 с / 300 с | 6 / 3 / 2 |

Почти все обрывы — OKX, код `1006`, класс резкий. Книги `books5`: p50 = 1 с, p99 = 3 с. Свечи `candle5m`: p50 = 2 с, p99 = 5 с. Bybit `orderbook.1` в этом срезе журнала — 3 обрыва по 1 с.

Три длинных восстановления 19-го (это уже настоящие дыры минутного масштаба):

| Длительность | Канал | Имя | Когда UTC |
|--------------|-------|-----|-----------|
| 1134 с (~19 мин) | `candle5m` | AERO | 01:25 → 01:44 |
| 303 с (~5 мин) | `candle5m` | LLY | 03:43 → 03:48 |
| 108 с | `books5` | CORE | 03:57 → 03:59, волна `wave_60s=10` |

Почему так бывает (механизм кода, не новая гипотеза биржи):

- планировщик подключений ~3 в секунду; в волне сотни сокетов ждут очередь;
- книги имеют приоритет выше свечей — свеча может ждать, пока поднимутся стаканы;
- бюджет повторного подключения на ключ: не больше 2 за час (`DEFAULT_BUDGET_MAX`), иначе пауза `reconnect_budget_exceeded`.

Отдельно: **календарные файлы без слота** — другая дыра. 16-го нет файлов `17:35` / `17:40` / `17:45`, потому что службу остановили в 17:32:36 и подняли в 17:51:18. Это рука оператора, не биржа.

Для модели: отсутствие тиков внутри слота ≠ спокойный рынок; отсутствие файла слота ≠ пять минут тишины, если процесс был выключен.

## 2. Откуда повышенный p99

Два разных числа. Их нельзя складывать.

| Величина | Что это | Сводно здесь |
|----------|---------|----------------|
| Доставка | `local_recv − ts` биржи | OKX p99 **200** мс, Bybit **223** мс |
| Возраст ноги до расчёта | `calc − local_recv`, порог 2 с | широкий ряд до 2000 мс — ожидание второй ноги, не сеть |

Прошлая узкая выборка 19-го (последние минуты + одно окно) дала доставку p99 342–400 мс. По 574 файлам локальной копии (`/root/mac_lean_pull`, 17-е целиком, куски 18-го и 19-го до 12:00, плюс час 18-го 15:00 с конечной копии) свод p99 ниже: **200 / 223** мс. Контракт «сводный p99 < 100 мс» на этом массиве **не** выполнен. Тихие часы его берут (17-е 21 ч: 75 / 73 мс) — как час 16-го 18:05–19:05 (80 / 61 мс).

Гистограмма доставки, доля строк:

|------------|-----|-------|
| 10–20 | 0 % | 53,5 % |
| 20–30 | 19,2 % | 42,4 % |
| 30–40 | 67,8 % | 1,5 % |
| 40–50 | 9,2 % | 0,45 % |
| 50–100 | 2,2 % | 0,65 % |

Отрицательных задержек нет. Выше 2500 мс: 6 строк OKX, 23 Bybit из 205 млн.

По часам 17-го p50 почти плоский (31–34 / 18–20 мс). p99 качается от 75 до 342 мс. Часы с большим числом строк (13–15 ч: 5,9–6,7 млн) дают p99 306–342 мс. Час 19-го 03:00 — **591 обрыв**, а p99 доставки только 158 / 186 мс: обрыв **вырезает** тики, а не делает оставшиеся медленными.

Час 18-го 15:00 (667 обрывов в длинном процессе): свод p99 376 / 421 мс при 6,3 млн строк — снова высокий поток, не «пять минут дыры».

**Факт:** пол / медиана = типичная доставка. Хвост — около 1,6 % строк > 100 мс.

**Допущение (согласуется с прежними прогонами скринер vs `ping`, не доказано этим срезом как единственная причина):** хвост — очередь одного цикла при N≈337, а не задержка биржи. Сопоставление с `ping` в этом отчёте не снимали. Задержку цикла (`loop lag`) не писали.

Возраст ноги до 2 с — следствие порога отказа записи, не хвост доставки.
